# بخش خدمات سلامت — دفتر خدمات سلامت ۴۷۷

راهنمای فنی و محتوایی بخش «خدمات سلامت» وب‌سایت. این بخش به‌صورت یک بخش مستقل
در کنار بخش خدمات صنعتی فعلی سایت ساخته شده و از همان زیرساخت، هویت بصری و
الگوهای موجود (Astro 5 + Tailwind v4 + i18n + JSON-LD) استفاده می‌کند.

---

## ۱. مسیرها

| مسیر | صفحه |
|---|---|
| `/health/` | «خدمات ما» — معرفی دفتر، فهرست دسته‌بندی‌شده خدمات، روند کلی، پیش‌نمایش دوره‌ها، تماس و مسیریابی |
| `/health/health-card/` | ثبت و صدور کارت بهداشت |
| `/health/hygiene-training/` | آموزشگاه بهداشت اصناف (+ فهرست دوره‌ها) |
| `/health/hygiene-qualification/` | خدمات صلاحیت بهداشت |
| `/health/audit-contracts/` | قراردادهای ممیزی |

این بخش **فعلاً فقط فارسی** است. به همین دلیل صفحات آن با `singleLocale` ساخته
می‌شوند: `hreflang` فقط به `fa` و `x-default` (همان نشانی) اشاره می‌کند و
سوییچ زبان در هدر پنهان است تا لینک شکسته (404) تولید نشود. اگر روزی نسخه
انگلیسی لازم شد، کافی است `singleLocale` برداشته شود و صفحه‌های `src/pages/en/health/`
ساخته شوند.

## ۳. افزودن یا ویرایش محتوا

### خدمت جدید
یک ورودی به آرایه `healthServices` در `src/content/health.ts` اضافه کنید:

```ts
const newService: HealthService = {
  slug: 'new-service',            // لاتین، کوتاه، با خط تیره → نشانی صفحه
  icon: 'heart',                  // از مجموعه src/components/health/icons.ts
  category: 'personal',           // باید در serviceCategories وجود داشته باشد
  status: 'active',               // 'active' | 'inactive'
  order: 5,                       // ترتیب نمایش
  seo: { title: '…', description: '…' },   // عنوان و توضیح متای اختصاصی
  copy: { /* title, summary, description, steps, documents, conditions,
             duration, fee, faqs, requestTypes, extraFields, disclaimer */ },
};
```

صفحه، کارت، فهرست جست‌وجو، sitemap، JSON-LD و «سایر خدمات» به‌صورت خودکار
ساخته می‌شوند.

### دسته‌بندی جدید
یک ورودی به `serviceCategories` اضافه کنید (id, label, description, icon).

### دوره جدید
به `courses` در همان فایل اضافه کنید. شناسه دوره (`id`) به‌طور خودکار در
select فرم ثبت‌نام ظاهر می‌شود و دکمه «ثبت‌نام در این دوره» با
`?course=<id>#request` فرم را پیش‌پر می‌کند.

### غیرفعال کردن موقت یک خدمت
`status: 'inactive'` → در فهرست با برچسب «غیرفعال» و کارت کم‌رنگ نمایش داده
می‌شود، صفحه اختصاصی آن اطلاعیه توقف ارائه را نشان می‌دهد و **فرم درخواست
حذف می‌شود** (تا درخواست بی‌پاسخ ثبت نشود).

### محتوای نیازمند تأیید مدیریت
هر فیلد حساس در قالب `ManagedField` ذخیره می‌شود:

```ts
documents: { approved: false, value: ['پیش‌نویس: …'] },
fee:       { approved: false, value: null },
```

- `approved: false` → برچسب «نیازمند تأیید مدیریت» + یادداشت توضیحی نمایش داده می‌شود.
- `value: null` → «اعلام‌نشده» / «پس از تأیید مدیریت اعلام می‌شود» نمایش داده می‌شود.
- پیشوند `پیش‌نویس:` در نمایش حذف می‌شود (فقط برای تشخیص در کد و تست است).
- تست `unapproved content is flagged…` اجازه نمی‌دهد داده تأییدنشده بدون
  برچسب منتشر شود.

پس از تأیید مدیریت: مقدار واقعی را بگذارید، `approved: true` کنید و پیشوند
«پیش‌نویس» را بردارید.

## ۴. فرم ثبت درخواست — وضعیت فعلی و اتصال به بک‌اند

### وضعیت فعلی (بدون بک‌اند)
فرم **رابط کاربری کامل** است: اعتبارسنجی، خطایابی دسترس‌پذیر، رضایت حریم
خصوصی، تله هرزنامه. اما چون بک‌اند اختصاصی آن راه‌اندازی نشده، داده‌ای ارسال
نمی‌شود و **موفقیت یا کد پیگیری ساختگی نمایش داده نمی‌شود**. در عوض:

1. بنر «وضعیت سامانه ثبت آنلاین» صادقانه اعلام می‌کند که فرم متصل نیست.
2. پس از ارسال معتبر، وضعیت «درخواست شما ارسال نشد» نمایش داده می‌شود همراه با
   سه راه واقعی: **تماس با دفتر**، **ارسال پیامک پیش‌پر شده** (`sms:` با متن
   خلاصه درخواست) و **کپی خلاصه درخواست**.
3. اطلاعات واردشده پاک نمی‌شود تا کاربر بتواند آن را کپی یا ویرایش کند.

### فعال‌سازی اتصال واقعی
متغیر محیطی را تنظیم کنید:

```
PUBLIC_HEALTH_FORM_ENDPOINT=/api/health-request/
```

فرم بلافاصله به همان نشانی `POST` می‌کند و فقط در صورت پاسخ موفق، کد پیگیری
بازگشتی از سرور را نمایش می‌دهد.

### قرارداد endpoint (بدون نیاز به تغییر فرم)

```
POST {PUBLIC_HEALTH_FORM_ENDPOINT}
Content-Type: application/json

{
  "locale": "fa",
  "service": "health-card",
  "requestType": "renewal",
  "name": "…", "phone": "…",
  "subject": "…", "message": "…",
  "consent": true,
  "organization": "…", "contactPerson": "…", "activity": "…", "course": "…",
  "clientStartedAt": "2026-10-10T12:00:00.000Z"
}

201 { "ok": true, "trackingCode": "477-123456", "status": "received" }
422 { "ok": false, "errors": { "phone": "phone", "message": "required" } }
429 { "ok": false, "error": "rate-limited" }
403 { "ok": false, "error": "forbidden-origin" }
```

انواع TS این قرارداد در `src/lib/healthRequests.ts` تعریف شده‌اند
(`HealthRequestPayload`, `HealthRequestAccepted`, `HealthRequestRejected`).

### گزینه‌های پیاده‌سازی بک‌اند
1. **توسعه `form-server/` موجود** (کم‌هزینه‌ترین): یک مسیر `/api/health-request`
   اضافه شود که `validateHealthRequest` را اجرا کند، رکورد را در
   `form-server/inbox/` یا SQLite ذخیره کند، `createTrackingCode()` را فقط پس از
   ذخیره موفق فراخوانی کند و پاسخ `201` بدهد. در توسعه، پروکسی `/api` در
   `astro.config.mjs` از قبل آماده است؛ در production باید مسیر `/api/*` به
   همان سرویس هدایت شود.
2. **Astro Actions + آداپتور SSR** (اگر سایت از حالت `output: 'static'` خارج شود).
3. **سرویس خارجی** (CRM یا فرم‌ساز): کافی است همان قرارداد را پیاده کند یا یک
   لایه نازک `FORM_WEBHOOK_URL`-مانند جلویش قرار گیرد.

### الزامات امنیتی و حریم خصوصی که بک‌اند باید رعایت کند
- اعتبارسنجی سمت سرور با **همان** `validateHealthRequest` (اعتماد به کلاینت ممنوع).
- محدودیت نرخ بر اساس IP + بررسی مبدأ (`ALLOWED_ORIGINS`) + تله هرزنامه +
  بررسی `clientStartedAt` (ارسال سریع‌تر از چند ثانیه = ربات).
- ذخیره **کمینه داده**: نام، شماره تماس، نوع خدمت/درخواست و توضیحات.
  اطلاعات هویتی (کد ملی) و سلامت **درخواست نمی‌شود** و نباید ذخیره شود.
- کنترل دسترسی: فقط نقش مدیر به فهرست درخواست‌ها دسترسی داشته باشد؛
  احراز هویت با رمز هش‌شده و نشست ایمن (HttpOnly + Secure + SameSite).
- کاربر دیگر هرگز نباید بتواند درخواست کاربر دیگری را ببیند؛ پیگیری فقط با
  کد پیگیری + شماره تماس (یا از طریق پنل مدیریتی).
- HTTPS اجباری (HSTS از قبل در `vercel.json` و `public/_headers` تنظیم شده).
- سیاست نگهداری: تعریف مدت نگهداری (مثلاً ۱۲ ماه) و حذف خودکار رکوردها؛
  ثبت دسترسی‌ها (audit log) برای تغییر وضعیت درخواست‌ها.
- اگر `connect-src` در CSP به دامنه دیگری نیاز دارد، `vercel.json` و
  `public/_headers` به‌روز شود.

### پنل مدیریت
پنل مدیریت عمداً ساخته **نشده** است، زیرا زیرساخت بک‌اند/پایگاه داده فعالی
وجود ندارد و ساخت یک پنل نمایشی با معیار «هیچ قابلیت نمایشی به‌عنوان قابلیت
عملیاتی معرفی نشود» در تضاد است. در عوض، مدیریت محتوا از طریق
`src/content/health.ts` انجام می‌شود (خدمت، ترتیب، متن، آیکون، هزینه، زمان،
دوره‌ها، سؤالات، اطلاعات تماس) و همه تست‌های یکپارچگی محتوا در
`tests/health.test.ts` از صحت آن محافظت می‌کنند.
پس از راه‌اندازی بک‌اند، پنل باید این موارد را پوشش دهد: افزودن/ویرایش/حذف
خدمات و تغییر ترتیب، مدیریت هزینه و زمان، مشاهده و تغییر وضعیت درخواست‌ها و
ثبت پاسخ مدیریتی، مدیریت دوره‌ها و ظرفیت، ویرایش سؤالات متداول و به‌روزرسانی
نشانی/شماره‌ها — همراه با احراز هویت و سطح دسترسی.

## ۵. تماس، مسیریابی و QR

- شماره‌ها: `۰۹۳۹۸۵۲۰۱۵۰` (همراه) و `۰۲۸۳۳۹۹۲۵۵۰` (ثابت) — در همه صفحات با
  لینک استاندارد `tel:` (قالب E.164).
- نشانی: قزوین، خیابان طالقانی، برج خلیج فارس، طبقه ششم، واحد ۶۱۹.
- «مسیریابی به دفتر»: `https://www.google.com/maps?q=36.2678594,50.0135519`
  (در تب جدید، `rel="noopener noreferrer"`).
- QR: با `npm run qr` از همان لینک نقشه ساخته می‌شود
  (`public/images/brand/office-location-qr.svg` و نسخه PNG چاپی). اگر نشانی یا
  مختصات عوض شد، این دستور را دوباره اجرا کنید.
- **نقشه تعاملی عمداً embed نشده است**: سایت هیچ درخواست شخص ثالثی ندارد و CSP
  فعلی (`frame-src` از `default-src 'self'`) iframe خارجی را مسدود می‌کند.
  در صورت نیاز به نقشه تعاملی، باید `frame-src https://www.google.com` (یا
  OpenStreetMap) به `vercel.json` و `public/_headers` اضافه شود.
- ساعات کاری تأییدنشده عمداً خالی است؛ به‌جای آن پیام «پیش از مراجعه تماس
  بگیرید» نمایش داده می‌شود.

## ۶. سئو

- عنوان و توضیح متای اختصاصی برای هر خدمت در `seo` همان خدمت.
- `<title>` صفحات این بخش با برند «دفتر خدمات سلامت ۴۷۷» ساخته می‌شود
  (`brand` در BaseLayout) نه نام سایت صنعتی.
- URL خوانا، `canonical`، `hreflang` (fa/x-default)، Open Graph، `og:site_name`.
- JSON-LD: `LocalBusiness` (با نشانی، تلفن و `GeoCoordinates`)، `Service`
  (با `provider` و `areaServed`)، `FAQPage` و `BreadcrumbList`.
- تیترها سلسله‌مراتبی: یک `h1` در هر صفحه، بخش‌ها `h2`، زیربخش‌ها `h3`.
- عبارات کلیدی (دفتر خدمات سلامت ۴۷۷ قزوین، خدمات کارت بهداشت در قزوین،
  آموزش بهداشت اصناف، خدمات صلاحیت بهداشت، قراردادهای ممیزی، نشانی دفتر) به‌صورت
  طبیعی در متن‌ها آمده‌اند؛ بدون تکرار مصنوعی و بدون ادعای تأییدنشده.
- صفحات در `sitemap-index.xml` و فهرست جست‌وجوی داخلی سایت هستند.

## ۷. دسترس‌پذیری و واکنش‌گرایی

- RTL کامل با Logical Properties (`ps-*`, `pe-*`, `ms-*`, `start-*`, `end-*`).
- فوکوس قابل مشاهده، `aria-invalid` + `aria-describedby` روی فیلدهای خطا،
  خلاصه خطا با `role="alert"` و فوکوس خودکار، `aria-live` برای وضعیت فیلتر/فرم.
- فیلتر و جست‌وجو، اشتراک‌گذاری و چاپ **افزایش تدریجی** هستند: بدون JS همه
  خدمات گروه‌بندی‌شده قابل مرورند و کنترل‌های JS-محور پنهان می‌مانند.
- آکاردئون سؤالات با `<details>` بومی (بدون JS).
- انیمیشن‌ها کوتاه‌اند و با `prefers-reduced-motion` خاموش می‌شوند.
- چیدمان در موبایل تک‌ستونه، در تبلت دو ستونه و در دسکتاپ سه ستونه +
  سایدبار چسبان (`lg:sticky`).

## ۸. ابزارهای کنترل کیفیت

```bash
npm test                      # ۳۰ تست: اعتبارسنجی فرم‌ها + یکپارچگی محتوای سلامت
npm run check                 # بررسی تایپ/Astro (۰ خطا)
npm run build                 # بیلد کامل سایت (۱۰۴ صفحه)
python3 scripts/qa-health.py  # بررسی خروجی بیلد بخش سلامت (پس از npm run build)
```

`scripts/qa-health.py` روی `dist/` اجرا می‌شود و این موارد را بررسی می‌کند:
`lang="fa" dir="rtl"`، نبود `hreflang="en"` و سوییچ زبان در صفحات تک‌زبانه،
canonical، حضور هر دو شماره `tel:`، لینک نقشه و تصویر QR، انواع JSON-LD
(`LocalBusiness`, `Service`, `FAQPage`, `BreadcrumbList`)، یکتایی `<title>`،
یک `h1` در هر صفحه، نبود شناسه تکراری، سالم بودن همه لینک‌های داخلی و لنگرها،
`https` بودن لینک‌های خارجی، وجود `<label>` برای همه فیلدهای فرم، و اینکه
صفحات انگلیسی به بخش فارسی لینک ندهند.
